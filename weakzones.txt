## 🧠 MINDSET: Think Like the Computer

Before tips, here's a key mindset:

> **Assume the computer does exactly what you said, not what you meant.**
> The bug is usually not in the logic, but in the details.

---

## ✅ PRACTICAL TIPS FOR HANDLING CORNER CASES

### 1. **Draw Small Input Examples (Manually)**

Run your code **by hand** on a small input like `{3, 1, 2}` or `{1, 2}` or `{}`. Write down:

* The value of each variable at every step.
* Where you enter and exit recursive calls.

This **immediately exposes off-by-one** or memory issues.

---

### 2. **Understand Array Boundaries**

This is **the #1 cause** of bugs in C:

* **For loop:** `for (i = 0; i < size; i++)` ✅
* `malloc(size * sizeof(...))` — always double-check `size` matches the number of **elements** you need (not `end - start` if inclusive).
* Is `start` inclusive? Is `end` inclusive or exclusive? Always **write this in a comment**.

👉 Example:

```c
// merge(array, p, q, r): merge array[p..q] and array[q+1..r] into array[p..r]
```

This makes future debugging MUCH easier.

---

### 3. **Use Assertions Early**

C has `assert()` in `<assert.h>`. Use it to catch logic errors as they happen.

```c
#include <assert.h>
// ...
assert(p <= q && q < r);
```

---

### 4. **Print Everything in Debug Mode**

Add debug prints to track:

```c
printf("merge(%d, %d, %d)\n", p, q, r);
printf("Left array: "); printArray(array, p, q);
printf("Right array: "); printArray(array, q+1, r);
```

Then comment them out or wrap in `#ifdef DEBUG` blocks later.

---

### 5. **Write Tests for Edge Cases**

For sorting:

* Empty array `{}`
* One element `{4}`
* Two elements `{2, 1}`
* All elements same `{5, 5, 5}`
* Already sorted `{1, 2, 3}`
* Reverse sorted `{3, 2, 1}`
* Duplicates `{4, 2, 2, 4}`

Write a loop that calls your sort function on all these, and checks if the result is sorted.

---

### 6. **Use `valgrind` to Check Memory**

If you're on Linux/Mac:

```bash
valgrind ./your_program
```

It will tell you if you're reading/writing out of bounds or leaking memory. Seriously helpful for malloc bugs.

---

### 7. **Comment Your Assumptions**

Before writing a function like `merge()`, write:

```c
// Assumes: p <= q < r
// Merges array[p..q] and array[q+1..r]
// Result is stored in array[p..r]
```

You'll catch inconsistencies faster just by writing them down.

---

## 🔁 Build Mental Habits

### 🔹 Always ask:

* Am I accessing memory out of bounds?
* What if size = 0? What if size = 1?
* Did I match `malloc` size to the number of elements?
* Am I passing inclusive or exclusive indexes?

### 🔹 When you're stuck:

* **Step through the code manually**, write down every variable on paper.
* **Reduce the input size** until it’s trivially traceable (e.g., 2 elements).
* Comment out complicated parts and reintroduce them step-by-step.

---

## 🧰 BONUS: Utilities for Debugging

Here’s a simple print utility for arrays:

```c
void printArray(int arr[], int from, int to) {
    printf("[");
    for (int i = from; i <= to; i++) {
        printf("%d", arr[i]);
        if (i != to) printf(", ");
    }
    printf("]\n");
}
```

✅ Write down function preconditions and postconditions

What you're describing is **very common**, and it’s not a sign of lacking intelligence — it’s about **mental fatigue**, **debugging mindset**, and the **stress response** when things don’t "just work." Let’s break this down and give you **tools and habits** to regain control when your mind blanks out.

---

## 🧠 WHY THIS HAPPENS

### 1. **Mental Exhaustion**

You've already burned energy writing and thinking hard about the problem. Now your brain is tired, and debugging feels like "extra punishment."

### 2. **Emotional Pressure**

You've invested time and feel it's “almost done.” The bug becomes an emotional block, not a technical one. Panic sets in: *"Why isn't it working? What am I missing?"*

### 3. **Lack of Process**

Debugging without a clear system leads to guesswork, frustration, and ultimately mental freeze.

---

## ✅ WHAT TO DO: THE “REBOOT + REBOOT” METHOD

Here’s a system to follow **exactly when** you feel your brain shutting down while debugging.

---

### 🌀 PHASE 1: REBOOT YOURSELF

1. **Stop Typing. Step Away.**
   Even 2 minutes walking around or stretching resets your mental cache. You must physically break the loop.

2. **Breathe + Label the Feeling.**
   Literally say to yourself:

   > “I feel stuck and overwhelmed. That’s okay. I’ve solved harder problems before.”

   This reduces emotional resistance. It’s not fluff — it’s neuroscience.

3. **Write (not think) what the bug is.**
   On paper or in a comment:

   ```c
   // Expected: [1, 2, 3]
   // Got: \[1, 3, 2]
   // Hypothesis: merge is misplacing elements after q
   ```

    ````
    Writing **slows down your thinking**, which is exactly what helps you regain clarity.

    ---

### 🔁 PHASE 2: REBOOT YOUR DEBUGGING APPROACH

Now with a clearer head, apply a systematic debugging flow:

---

### 🔎 1. **Minimal Input Test**
Reduce the problem to the **smallest possible failing case.**

Example: If you're sorting 100 elements, try just 2 or 3:
```c
int A[] = {2, 1};
````

If that fails, it's easy to trace.

---

### 🧩 2. **Print Key Variables**

Identify 3–5 values that are essential to your logic, and print them **before** the bug happens.

```c
printf("merge(%d, %d, %d)\n", p, q, r);
printArray(array, p, r);
```

Don’t just guess. Print what actually happens. You'll often find the bug without even trying hard.

---

### 🧱 3. **Assert Assumptions**

Start writing things like:

```c
assert(p <= q && q < r);
assert(array != NULL);
```

You’ll be amazed how quickly this catches logical errors you thought "couldn't happen."

---

### 🪞 4. **Trace With Comments**

Use comments to trace logic:

```c
// Before merge: [2, 1]
// Left = [2], Right = [1]
// Should become [1, 2]
```

You often spot inconsistencies just by describing what should happen.

---

### 📤 5. **Ask ChatGPT or a Friend — But Show Your Thoughts**

If you get stuck, **show your reasoning** when asking:

> “I expected merge(\[2], \[1]) → \[1, 2], but got \[2, 1]. I think maybe my copy logic skips an index.”

Explaining it clearly is often enough to make the solution pop into your own head.

---
